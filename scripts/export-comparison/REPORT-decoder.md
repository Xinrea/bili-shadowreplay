# 自动视频解码线程：macOS / Windows 实测

2026-10-31，测量源码 `bb178953e05fec80a79d8cf5cc8c80938469603e`。沿用五分钟 1080p60、每秒 20 条文字／表情的场景，**默认自动解码线程使 macOS 总耗时减少 29.64%，Windows 减少 21.36%**。这是各平台内三次关闭阶段计时的进程墙钟中位数。

## 实现与范围

- `MediaInput.decoder_threads` 未设置时，视频解码器在打开前设置 `thread_count=0`，由 FFmpeg 选择支持的帧／切片并行方式。它直接成为生产默认行为，无须开启新 feature 或配置。
- 本场景的 H.264 解码器在 macOS 实际使用 **13 个线程**，Windows 使用 **16 个线程**，两端 `active_thread_type=1`；单线程对照均为 `1 / 0`。显式正整数限制、图片输入的单线程设置和 AVOptions 覆盖顺序保留，音频继续使用原有默认值。
- 自动帧线程会缓冲尾帧。回归测试发现 3240×2160 视频在 EOF 时一次性接收尾帧可能超过复杂图原有的 64 MiB pending 队列上限；现改为按调度器需求逐帧排空。**没有扩大队列上限**，也不重复发送 EOF。
- 保留 MediaPlan、Skia Vulkan、Windows Vulkan Video 以及 macOS MoltenVK + VideoToolbox。未改变 GPU 同步、合成、编码或音频策略，没有新增合成结果的 CPU 帧回读。输入仍由软件解码并上传 NV12，不能将本轮称为硬件解码或全链路零拷贝。

实现提交：`5e6d8cd8`（默认解码并行及对照工具）、`bb178953`（按需排空 EOF 尾帧）。

## 场景与对照方式

- macOS：M2 Max，12 CPU / 38 GPU、64 GiB，macOS 27.0.1，FFmpeg 9.0.2、MoltenVK 1.4.2。
- Windows：Ryzen 9 5900X，12 核 / 24 线程，RTX 5070，约 48 GiB 内存，驱动 617.42，FFmpeg 9.0.2。两台机器规格不同，不把绝对耗时差解释为操作系统差异。
- 同一段 300 秒 Big Buck Bunny 视频、1080p60、18,000 帧；每秒 16 条文字 + 4 条 PNG 表情，共 6,000 条。两端素材及场景文件逐项核对 SHA-256。
- 项目默认 HEVC / 速度优先 / 10 Mbps、GOP 120，复制源 AAC。每次都要求并确认 GPU 帧处理器，三帧异步合成队列。两种模式的编码器配置相同。
- 各平台使用**同一个 release 二进制**：基线通过 `--decoder-threads 1` 复现此前单线程默认行为；自动组省略覆盖参数，使用新的生产默认值。基线同样包含 EOF 修复，这不是两个不同版本二进制的比较。
- 两种模式各预热 600 帧，随后运行三组关闭阶段计时的完整对照，顺序为“单→自动、自动→单、单→自动”。最后另跑一组开启阶段计时的完整诊断。每台主机的 GPU 作业及校验串行，校验不计入导出时间。
- 总耗时是启动到退出的进程墙钟，包含初始化、能力探测和文件发布。主结论只使用六个关闭计时的完整导出；预热和诊断不进入中位数。三次重复用于观察波动，不是统计置信区间。

## 分阶段诊断

下表每种模式只有**一次独立的完整诊断运行**，用于解释趋势；不是三次平均。数值是 worker API 的排他墙钟，包含阻塞，父子阶段已扣除，可以相加。它们不是各阶段的 CPU 消耗，也不是 GPU shader／硬件编码器执行时间。端到端中位数与该表来自不同运行，不应相减求精确归因。macOS 的自动线程诊断仅耗时 66.803 s，比三次正式性能样本都快；保留这项波动记录，但不据此上调主结论的加速比例。

| 阶段 | macOS 单线程 | macOS 自动 | Windows 单线程 | Windows 自动 |
| --- | ---: | ---: | ---: | ---: |
| 视频解码 send + receive | 41.927 s | 0.259 s | 46.820 s | 0.291 s |
| CPU 基础滤镜 | 2.866 s | 2.968 s | 6.147 s | 8.079 s |
| Skia 绘制及提交 | 9.581 s | 9.714 s | 9.860 s | 9.538 s |
| NV12 底图上传 API | 2.529 s | 2.428 s | 5.908 s | 6.259 s |
| libplacebo 合成 API | 17.329 s | 17.586 s | 19.940 s | 17.329 s |
| 在途帧槽复用／收尾等待 | 0.090 s | 0.090 s | 0.836 s | 21.182 s |
| VideoToolbox 交接前等待 Vulkan | 27.607 s | 23.647 s | — | — |
| Metal 交接 API（含完成等待） | 5.256 s | 4.815 s | — | — |
| 编码器 send / receive / EOF API | 3.686 s | 3.151 s | 2.424 s | 9.069 s |
| 读取、封装与文件收尾 | 0.917 s | 0.832 s | 0.832 s | 0.771 s |
| 其余调度、帧池、初始化及清理 | 0.896 s | 0.805 s | 2.265 s | 2.153 s |
| **worker 总计** | **112.685 s** | **66.294 s** | **95.031 s** | **74.672 s** |

解码 API 对 worker 的占用从 macOS 的 41.927 s 降至 0.259 s，Windows 从 46.820 s 降至 0.291 s。FFmpeg 把解码工作放到内部线程，与后续渲染／编码推进重叠，故 **API 占用减少不等于解码 CPU 工作量消失**。

自动线程后，macOS 的 Vulkan→VideoToolbox 交接前等待仍有 23.647 s，libplacebo API 为 17.586 s；Windows 的帧槽复用／收尾等待增至 21.182 s，编码 API 为 9.069 s，libplacebo API 为 17.329 s。帧槽复用会等待 overlay、底图和输出帧的最新 timeline semaphore，包含合成和编码消费者的依赖。这表明 Windows 的主要阻塞转向 GPU／编码消费进度，但当前计时尚不能拆分各消费者的设备执行时间。解码供给变快也会改变后续阶段的阻塞分布，不能把单线程的解码耗时直接从总时间中扣除来预测收益。

后续应验证 macOS 延迟交接／就绪帧队列，减少 worker 的逐帧等待；Windows 则应先区分帧槽复用是在等待合成还是编码，再评估队列深度与提交节奏。两端都需要 GPU 时间戳或 capture 才能分清 libplacebo 的提交成本、设备执行和队列等待，不能仅凭宿主 API 时间就改写 shader 或盲目加深队列。本轮未实现这些后续优化。

## 资源代价

macOS 使用 `/usr/bin/time -l`，以下为三次未开启阶段计时运行的中位数。CPU 秒为进程 user + system，平均核数为该 CPU 时间除以进程墙钟；RSS 是进程驻留内存指标，不能代表全部 GPU 分配。

| 模式 | 总 CPU 时间 | 平均占用 CPU 核数 | 最大 RSS |
| --- | ---: | ---: | ---: |
| 单线程 | 122.66 s | 1.13 | 207.9 MiB |
| 自动线程 | 130.84 s | 1.72 | 297.1 MiB |

多线程允许更多工作同时推进，并增加解码帧缓存及线程资源；仍可通过结构化输入字段显式限制线程数。Windows 本轮没有采集同等口径的 CPU 秒和峰值 RSS，不能据此给出其内存开销比例。

## 验证与可复现记录

- 两端共 **16 个五分钟产物 + 4 个预热产物**全部通过完整解码帧数和 PTS 网格、AAC 包载荷一致性、文字及 PNG 表情采样检查；完整产物均为 18,000 帧，预热均为 600 帧。
- 所有诊断／预热验证真实线程数、GPU 帧处理器和三帧异步队列；上传、提交、输出计数一致，排他时间分摊误差小于 0.001 ms。macOS 每帧均有有效 Metal blit GPU 时间戳。
- macOS 原生 `ffmpeg_utils` 测试 **141 通过**；Windows release 新增解码回归 **3 通过**。覆盖实际线程配置及显式覆盖、11 帧 B-frame 短片、两种执行器、输入精确 seek、输出裁剪、音频复制、EOF，以及高分辨率 327 帧尾部排空。短片对照要求编码包和时间戳与单线程一致。
- 两端 release 构建通过；实现提交的格式、普通／headless Clippy 与测试钩子通过。
- Windows 使用临时隔离源码，原工作区原先的三处改动保留。新生成媒体仅在验证及 SHA-256 记录成功后删除，JSON 回执和采样图保留；macOS 产物保留在回执所列临时目录。
- 早期 `5e6d8cd8` 探索运行在发现独立的高分辨率 EOF 问题后主动中断，不纳入任何表格；这里所有结果均来自修复后的 `bb178953`。
- **本轮没有重跑 #459**。[此前与 #459 的对照](REPORT-shared-gpu.md)是独立实验，不能与这里的线程对照混作同一批数据。
