# GPU 编码帧异步交接：macOS / Windows 实测

2026-10-31，测量实现 `5b8df1575f8ea91d8ad67adc9274e0ae77a3a541`。五分钟 1080p60、每秒 20 条文字／表情、项目默认编码参数下，**macOS 异步交接使导出耗时减少 35.28%**。主结论使用各组三次关闭阶段计时的进程墙钟中位数。

## 已落地的改动

- macOS 的 Vulkan→Metal→VideoToolbox 交接由逐帧阻塞改为最多三帧的在途队列，默认启用。就绪检查每次只做一次，不忙等；队列满或 EOF 时才阻塞推进。沿用 MediaPlan、Skia Vulkan、MoltenVK 和 FFmpeg VideoToolbox。
- 帧按提交顺序交给编码器；EOF 先排空合成器，再排空交接队列，最后结束编码。取消或错误时，Metal 命令完成前保留源 Vulkan 帧、目标 IOSurface 和纹理视图，避免 GPU 使用已释放或被复用的图像。
- 所有状态仍由原 media worker 管理，没有新增跨线程 Skia/Vulkan 对象共享。原有三帧合成限制和八帧处理器安全上限保留。
- Windows 保留 Vulkan Video 的直接 GPU 帧／timeline 交接。本轮是其共享接口的回归验证，未改变 Windows 提交或编码策略。
- 合成结果没有 CPU 帧回读。macOS 仍有一次 GPU NV12→IOSurface blit；输入仍为软件解码后上传 NV12，因此不是全链路零拷贝或硬件解码。

## 对照方法

- macOS：M2 Max，12 CPU / 38 GPU、64 GiB，macOS 27.0.1；FFmpeg 9.0.2、MoltenVK 1.4.2。用同一个 release 二进制，`--blocking-handoff` 复现阻塞交接；当前组省略参数，使用生产默认异步交接。
- Windows：Ryzen 9 5900X，12 核 / 24 线程，RTX 5070，驱动 617.42、约 48 GiB 内存；FFmpeg 9.0.2。基线使用保留的 `bb178953` 二进制，SHA-256 为 `c66694f23274a1212d51d59b37740abd1fd94c1e6ee3d854cd3d9892950a8b95`；当前二进制来自 `5b8df157`。两者自动解码优化相同。
- 两端使用相同哈希的视频和场景：300 秒、1920×1080、60 FPS、18,000 帧；每秒 16 条文字和 4 条 PNG 表情，共 6,000 条。默认 HEVC / 速度优先 / 10 Mbps / GOP 120，复制源 AAC；全部要求真实 GPU 帧处理器。
- 两种模式都用自动解码线程，macOS 实际 13 线程、Windows 16 线程，`active_thread_type=1`。不会把前一轮解码并行收益计入本轮。
- 每端先各预热 600 帧，再运行三组关闭 profiling 的完整对照，顺序为“基线→当前、当前→基线、基线→当前”，最后单独运行一组开启 profiling 的诊断。每台机器串行运行 GPU 作业及产物校验，没有同时编译。
- 每次计时覆盖进程启动至退出，包括初始化、能力探测和文件发布。完整解码 PTS、AAC 包一致性、文字／表情采样校验位于计时外。三次重复用于观察波动，不能据此给出统计置信区间。

## 分阶段诊断

以下各模式仅一次完整诊断，和上表中位数来自不同运行。数据是 **worker API 排他墙钟，包含阻塞**；不是 CPU 秒或 GPU shader／编码器执行时间。父子阶段已扣除，可相加。Metal GPU 时间戳另存为重叠 observation，不加入本表。

| 阶段 | macOS 阻塞 | macOS 异步 | Windows 基线 | Windows 当前 |
| --- | ---: | ---: | ---: | ---: |
| 视频解码 send + receive | 0.264 s | 0.461 s | 0.298 s | 0.295 s |
| CPU 基础滤镜 | 3.046 s | 3.589 s | 7.381 s | 7.569 s |
| Skia 绘制及提交 | 10.154 s | 10.324 s | 9.752 s | 9.859 s |
| NV12 底图上传 API | 2.530 s | 2.540 s | 6.387 s | 6.241 s |
| libplacebo 合成 API | 17.919 s | 17.975 s | 17.103 s | 18.520 s |
| 在途帧槽复用／收尾等待 | 0.086 s | 3.389 s | 21.448 s | 21.211 s |
| 交接前阻塞等待 Vulkan | 25.301 s | 0.000 s | — | — |
| 交接前 Vulkan 就绪检查 | 0.000 s | 0.336 s | — | — |
| Metal 提交／完成检查／等待 | 5.249 s | 0.581 s | — | — |
| 编码器 send / receive / EOF API | 3.180 s | 3.484 s | 9.484 s | 8.218 s |
| 读取、封装及文件收尾 | 0.818 s | 0.943 s | 0.778 s | 0.752 s |
| 其余调度、帧池、初始化及清理 | 0.894 s | 0.856 s | 2.174 s | 2.091 s |
| **worker 总计** | **69.441 s** | **44.478 s** | **74.805 s** | **74.757 s** |

macOS 的 Vulkan 交接前阻塞从 25.301 s 降至 0 s（此次异步诊断未发生该阻塞），Metal 完成等待从 4.648 s 降至 0.011 s；就绪检查约 0.336 s。与此同时，帧槽复用等待从 0.086 s 增至 3.389 s，基础滤镜、解码与编码 API 占用也略有增加，因此不能把减少的等待直接相加当作端到端收益。这次独立诊断的 worker 总时间从 69.441 s 降至 44.478 s，与未开启 profiling 的三轮结果方向一致。

Metal blit 的 GPU 时间戳区间累计时长从 0.654 s 增至 1.294 s；这些是可与其他阶段重叠的设备区间，未并入上表。总 CPU 时间也略有上升。本轮收益来自工作重叠和减少宿主阻塞，不表示 GPU blit 或解码本身更便宜。

macOS 当前最大的两个宿主 API 阶段是 libplacebo 合成约 17.975 s 和 Skia 绘制／提交约 10.324 s。Windows 当前仍主要阻塞在帧槽复用／收尾约 21.211 s，libplacebo 合成 API 约 18.520 s。Windows 两次诊断的 libplacebo 与编码 API 时间有相反方向的变化，而 worker 总时间均约 74.8 s；不能把这类单次阶段变化当作新增回归或收益。

libplacebo、帧槽等待和编码 API 的墙钟尚不能分离设备执行与队列依赖。后续应拆分帧槽等待所对应的合成／编码消费者，并采集 GPU 时间戳，再决定是否调整提交节奏或队列深度。

## 验证与限制

- 两端 **16 个五分钟产物 + 4 个预热产物**全部通过完整解码帧数／PTS 网格、AAC 包载荷一致性、文字及 PNG 内容采样检查。完整产物均为 18,000 帧、8 个内容采样时刻；预热为 600 帧、3 个采样时刻。
- macOS 诊断记录每次交接提交数等于完成数，结束时 pending 为 0；阻塞模式峰值 1 帧，异步模式不超过 3 帧。每帧均有有效 Metal blit GPU 时间戳。两端计时排他分摊误差小于 0.001 ms，合成／上传／输出计数一致。
- macOS 原生 `ffmpeg_utils`：**145 通过、1 个需 Vulkan Video 的测试忽略**。新增实际 GPU 测试 **2 通过**，覆盖 H.264／HEVC、1／2／3／7 帧尾部、顺序与时长、取消和失败清理；已有真实视频／音频／时序内容以及双编码器 GPU 测试 **2 通过**。
- Windows 原生 Vulkan 测试 **5 通过**，包括真实 GPU frame lease 生命周期、取消／失败后的原目标保护。使用临时最小 workspace，81 个依赖包版本／校验和均与项目 Cargo.lock 一致，crate 源码逐文件核对。
- 两端 release 导出构建通过；实现提交的格式、普通／headless Clippy 与测试钩子通过。**Windows 完整 GUI 测试构建因磁盘不足未完成**，不能将原生测试和导出验证表述为完整 GUI 测试通过。已清理该次失败构建新生成的文件；实际性能数据由已成功构建的 release 导出程序产生。
- Windows 使用隔离临时源码，原工作区原先三处改动保留。运行时七个 FFmpeg DLL 与已记录哈希一致；曾缺失的临时 SDK 从现有归档恢复，不更换 FFmpeg 版本。新生成媒体仅在通过验证并记录 SHA-256 后删除，JSON 回执与采样图保留。
- 短片 smoke 的耗时不计入任何性能表。本轮没有重跑 #459，不能与此前独立批次的 #459 结果拼成新的受控对照。
