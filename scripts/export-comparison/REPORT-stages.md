# 当前共享 GPU 导出的分阶段实测

2026-10-31，源码 `ca699326d5658e6881ecee9ad87bdc11062ccb06`。结论：**优先验证解码并行，其次解除 macOS 的逐帧交接等待，再深入分析 libplacebo。** Metal 纹理包装／缓存清理和文字排版不是本轮的主要耗时项。

沿用生产 MediaPlan、Skia Vulkan、Windows Vulkan Video / macOS MoltenVK + VideoToolbox，没有修改解码线程、编码参数或同步策略。计时工具不增加 GPU 同步，不回读像素。

## 场景与方法

- M2 Max（12 CPU / 38 GPU、64 GiB、macOS 27.0.1）；Ryzen 9 5900X + RTX 5070（约 48 GiB、驱动 617.42）。硬件与上轮一致；不把跨机器的绝对差异解释为操作系统差异。
- 同一段五分钟 1080p60 视频，18,000 帧；每秒 16 条文字 + 4 条 PNG 表情，共 6,000 条。素材、场景和表情哈希均核对。
- 项目默认 HEVC / 速度优先 / 10 Mbps，GOP 120，复制源 AAC。两端均确认 `frame_processor=true`，三帧异步队列，输入上传与输出均为 18,000 帧。
- 各平台内使用同一 release 二进制，先各预热 600 帧，然后按“关闭→开启、开启→关闭、关闭→开启”运行三组。每台机器的导出和校验串行，校验不计入导出时间。
- 阶段表是三次开启计时的 **worker API 排他墙钟时间均值**，包含 API 内部阻塞，不是各阶段 CPU 使用时间或 GPU 执行时间。子阶段已扣除，表中各行可以相加。
- 端到端表是进程启动至退出的中位数，还包含加载、能力探测、场景准备和发布。它与阶段均值不是同一统计量。

| --- | ---: | ---: | ---: |
| macOS / 关闭 | 106.510 s | 115.895 s | 117.291 s |

Windows 的开关差值接近零。macOS 对照组自身也有明显波动，开启计时相对中位数增加约 3.56%；不能将全部差值确定为计时器本身的固定开销。下列阶段值来自开启计时的实际运行，没有缩放成关闭计时的数据。三次重复用于观察本机波动，不构成统计置信区间。

## 阶段分摊

| 阶段 | macOS 均值 | macOS 占比 | Windows 均值 | Windows 占比 |
| --- | ---: | ---: | ---: | ---: |
| 视频解码（send + receive） | 43.027 s | 36.32% | 46.618 s | 49.15% |
| CPU 基础滤镜 | 3.026 s | 2.55% | 6.212 s | 6.55% |
| Skia 绘制及提交 | 9.917 s | 8.37% | 9.938 s | 10.48% |
| NV12 底图上传 API | 2.666 s | 2.25% | 5.921 s | 6.24% |
| libplacebo 合成 API | 18.016 s | 15.21% | 19.879 s | 20.96% |
| 在途帧槽复用／收尾等待 | 0.091 s | 0.08% | 0.840 s | 0.89% |
| VideoToolbox 交接前等待 Vulkan 完成 | 30.206 s | 25.50% | — | — |
| Metal 交接 API（含完成等待） | 5.830 s | 4.92% | — | — |
| 编码器 send / receive / EOF API | 3.883 s | 3.28% | 2.411 s | 2.54% |
| 读取、封装与文件收尾 | 0.847 s | 0.72% | 0.831 s | 0.88% |
| 其余调度、帧池、初始化及清理 | 0.949 s | 0.80% | 2.193 s | 2.31% |
| **worker 总计** | **118.457 s** | **100%** | **94.844 s** | **100%** |

两端每一轮的真实解码器配置都是 `thread_count=1, active_thread_type=0`。解码工作主要发生在 `send_packet`，不能仅看 `receive_frame` 的耗时。

`libplacebo`、Skia、上传、编码行均是宿主调用时间，可能包含驱动内部等待。**这里没有隔离出这些阶段的 GPU shader / 硬件编码执行时间**；不能把编码 API 占比小等同于硬件编码器完全没有开销。

## macOS 的等待究竟在哪里

以下是与阶段表重叠的细分观察量，**不要再次加到总时间里**。仅 GPU blit 一行使用 Metal 命令缓冲的设备时间戳，读取发生在原有完成等待之后。

| 观察量 | 三次均值 |
| --- | ---: |
| Metal 命令与纹理准备（包含纹理包装） | 0.561 s |
| 其中：两个 CVMetalTexture 包装 | 0.169 s |
| Metal commit 调用 | 0.081 s |
| CPU 等待 Metal 命令完成 | 5.051 s |
| 释放纹理包装与缓存 flush | 0.068 s |
| **GPU 实际 blit 命令区间** | 0.997 s |

Vulkan 完成等待三次分别为 26.459 s、31.355 s、32.804 s。它等待底图上传、Skia 和合成的前置依赖，不能直接等同于 libplacebo shader 的执行时间。

Metal GPU blit 本身很短；纹理包装和缓存清理也很小。当前更大的问题是 worker 逐帧停下来等待完成，等待期间不能继续推进后续视频帧的解码和提交。后续应验证延迟交接、就绪帧队列以及在帧槽复用时再等待的收益，而非先重写纹理缓存。

## Skia 细分与优化顺序

| Skia 观察量（相互包含，不能重复相加） | macOS | Windows |
| --- | ---: | ---: |
| 场景绘制调用（含文字／图片准备） | 4.290 s | 5.510 s |
| flush / submit 调用 | 5.408 s | 4.142 s |
| 文字排版 | 0.582 s | 0.605 s |
| 文字贴图准备 | 0.351 s | 0.403 s |
| 图片准备 | 0.002 s | 0.003 s |

1. **先做解码线程的受控 A/B。** 两端的最大单项都是单线程解码。#459 显式使用自动解码线程，并将解码、渲染、编码分到不同线程；当前应先单独验证自动／有界多线程解码的收益，再测阶段重叠，避免同时改动多个因素。
2. **macOS 推迟完成等待，允许阶段重叠。** 保留 MediaPlan 与 Skia Vulkan / MoltenVK，把等待从每帧的紧邻调用处推迟到真正需要结果或复用资源时。需继续验证帧池所有权、顺序、取消和收尾。
3. **再分析 libplacebo 与 Skia 提交。** libplacebo API 仍是两端的重要耗时项；需 GPU 时间戳或独立 capture 才能分清命令构建、队列等待和 shader 执行。不应只凭本表就把该耗时全部归因于 shader，或直接换掉合成后端。
4. **暂缓优化小项。** 本场景中文字准备、Metal 纹理包装／缓存清理、封装都不是首要耗时；编码 API 的阻塞占比也较低。

本轮只给当前生产路径加计时，没有给 #459 加同样的阶段探针。[此前的 #459 对照](REPORT-shared-gpu.md)仍是独立的整机墙钟实验，其编码默认值和 macOS CPU 忙等线程等差异仍存在；本报告定位当前路径的优先项，不能把两实现的全部差距定量归因给某一个阶段。

## 验证、保存与复现

- 12 个五分钟产物和 4 个预热产物全部通过：完整解码帧数／时间戳、AAC 包载荷一致性、文字及 PNG 表情采样。所有开启计时的导出均检查排他时间分摊和逐帧计数；macOS 每帧均取得有效 Metal GPU 时间戳。
- 普通版与 headless 的 Clippy、测试通过；额外通过计时器嵌套／隔离／异常清理测试和原生帧处理器的时间戳、音频、收尾、错误保全测试。两端 release 构建及实际 GPU 导出通过。
- Windows 使用已有临时隔离源码副本；原工作区保留原先三处改动。为控制空间，本轮 Windows 媒体在成功验证及记录 SHA-256 后删除，JSON 回执与采样图保留。
