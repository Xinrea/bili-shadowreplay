# Windows：最新版与 #459 的三轮交替对照

2026-10-31，在同一台 Ryzen 9 5900X（12 核／24 线程、约 48 GiB）+ RTX 5070
（12 GiB、驱动 617.42）、Windows build 26100 上重新测量。
当前媒体源码固定 `1cd0c881`（含共享 compute 与 sRGB 支持），#459 固定
`c73c7aaff9b9dd9abb561c90a48f19b2d6374112`。测量工具在 `ae130211`。
两边均使用 release、同一 FFmpeg 9.0.2 SDK/DLL 和 Skia 0.82.0 Vulkan 包。

## 默认导出的总耗时

| 实现 | 三轮未开启阶段计时的耗时（秒） | 中位数（秒） | 极差（秒） |
| --- | --- | ---: | ---: |
| 最新版 | 74.099 / 74.370 / 74.496 | **74.370** | 0.397 |
| #459 | 74.049 / 74.059 / 74.129 | **74.059** | 0.079 |

中位数相差 **0.311 秒**；最新版相对 #459 的耗时变化
为 **+0.42%**。这组输入下两者实际吞吐基本一致，
没有复现以前明显落后的结果；三次重复不能证明所有输入、显卡或驱动都持平。
按完整进程墙钟折算，最新版 **242.0 fps / 4.03 倍实时**，
#459 **243.0 fps / 4.05 倍实时**。

输入仍是连续五分钟 1080p60 的 Big Buck Bunny，18,000 帧、SDR BT.709；
每秒 16 条文字 + 4 条 PNG 表情，共 6,000 条事件，滚动 8 秒。
两边使用项目默认 HEVC、速度优先、10 Mbps、1080p60，复制源 AAC。
素材和场景逐文件 SHA-256 与之前测试一致。独立 CPU 参考图复用此前已验证的
Windows 场景，重新核对素材／场景哈希及参考文件；不在计时期间生成参考图。

每个二进制先预热 600 帧。正式对照按“当前→PR、PR→当前、当前→PR”执行；
每组后再同顺序做一次独立的阶段诊断，共 6 次正式对照、6 次完整诊断、3 次预热。
总耗时用原始未加计时的 #459 二进制；阶段诊断用只加计时的独立副本。
最新版同一个二进制分别关闭／开启 `--measure-stages`。每次只运行一个导出，
完整校验在计时之外、下一次导出之前执行；计时期间没有并行编译或其他基准。

外部计时覆盖进程启动、场景解析、能力探测、解码、归一化、GPU 绘制、合成、
编码、封装及成功退出。复用正式媒体模块的独立 runner，未启动 GUI/V8/语音；
准备素材与弹幕布局、录播分段缓存调度和上传不在本次范围内。
当前全部使用 `--require-gpu`，确认 `hevc_vulkan`、`frame_processor=true`、
`vulkan-nv12-compute-v4-srgb`，没有把 CPU 回退计为 GPU 结果。

## 目前的差距与下一步重点

| 三次正式对照的逐轮中位数再取中位数 | 最新版 | #459 |
| --- | ---: | ---: |
| NVIDIA GPU utilization | 9.0% | 8.0% |
| NVIDIA encoder utilization | 97.0% | 97.0% |
| NVIDIA decoder utilization | 0.0% | 0.0% |
| GPU 温度 | 45.0 °C | 45.0 °C |
| SM 频率 | 2947 MHz | 2947 MHz |

遥测每秒采样一次，记录整张显卡，不是进程归属或 GPU 执行时间；不能由低 GPU
utilization 推断硬件编码器空闲。两边软件解码，decoder utilization 为零符合路径。

结合编码单元约 97% 利用率、当前送帧 API 中的大量时间、#459 下游队列的等待，
**这组默认配置更接近受编码吞吐限制，而非 compute 合成不足**。这是多项测量支持的
判断，不是已经测得所有硬件编码场景的上限。两边 compute 宿主提交都约 1 秒量级，
继续压缩这一项或增加渲染线程，不能预期同比缩短总耗时；被省出的时间可能变为
等待编码器。当前送帧时间短于 #459，也主要与工作重叠、等待落点不同有关。

若继续优化本场景，优先对编码参数／提交策略做保持输出要求的受控实验，
并结合画质验证；本轮不改默认参数或产品实现，不宣称额外队列一定有效。
Windows 的 Skia、上传和帧复用开销仍存在，但现有数据没有显示它们造成对 #459
的明显端到端落后。

历史 Windows 同场景：旧共享 libplacebo 版本为 96.748 s，自动并行解码后为
75.435 s，上一轮 handoff 版本为 75.321 s。本次是最新 compute 版本和 #459 的同期
重测；旧版本没有重新运行，不能把相邻报告的差值全归因于一次 shader 改动。
历史来源：[共享 GPU](REPORT-shared-gpu.md)、[解码优化](REPORT-decoder.md)、
[异步交接](REPORT-handoff.md)。本报告的 #459 数据来自 RTX 5070 上的 Windows 重测；
PR [README](https://github.com/Xinrea/bili-shadowreplay/blob/c73c7aaff9b9dd9abb561c90a48f19b2d6374112/src-tauri/crates/gpu-export/README.md)
提到的 Linux / RTX 4090 是另一环境，macOS 结果也没有混入此表。

## 输出默认值与验证

| 项目 | 最新版 | #459 |
| --- | --- | --- |
| 编码器 | hevc_vulkan | hevc_vulkan |
| 显式编码选项 | async_depth=3、rc_mode=vbr | quality=0 |
| 实际最大 GOP 间隔 | 120 | 300 |
| I / P / B 帧数（每个完整输出） | 150 / 6000 / 11850 | 60 / 6000 / 11940 |
| 实际视频码率中位数 | 9.962 Mbps | 9.973 Mbps |

两边保留实际默认编码策略，所以这是默认导出体验比较，不是严格等画质、相同
GOP/B 帧配置的性能测试。`has_b_frames=1` 是重排字段，不是 B 帧数量。
本次输入是 BT.709，当前 sRGB 分支计数为零，不能当作 Windows sRGB 颜色专项验证。

全部 **15 个产物**（12 个五分钟、3 个十秒预热）通过完整解码，共 **217,800 帧**：
连续 CFR PTS、HEVC 尺寸／帧率／时长、AAC 包载荷一致；12 个完整输出各有
8 个文字和 PNG 采样点，包括 299.9 秒尾部。当前三次诊断均观测到
submitted/output/uploaded=18000、在途峰值 3。独立 CLI 仅用于计时外的验证。
这不等同于逐像素一致、等感知画质或新一轮完整 Vulkan validation layer 审计。

由于 C 盘空间有限，每个新增视频仅在全部验证通过、记录 SHA-256 后删除；
日志、采样图与回执保留。构建和测试都在临时隔离目录；用户 Windows 工作区
仍保持原来的三个修改。二进制、SDK DLL、当前源码和 PR 计时副本的哈希在结束后
再次核对一致；本轮没有改动生产导出逻辑。
