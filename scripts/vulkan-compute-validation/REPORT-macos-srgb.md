# macOS sRGB input validation

Validated on 2026-10-31, Apple M2 Max / macOS 27.0.1, FFmpeg 9.0.2,
MoltenVK 1.4.2. This extends the existing shared compute compositor; MediaPlan,
Skia Vulkan and both encoder adapters are retained.

## Colour contract

The video prefilter still normalizes the YCbCr matrix/range to limited BT.709
NV12 without overriding the source transfer. For `iec61966-2-1`, the GPU shader
reconstructs nonlinear RGB, decodes sRGB, encodes BT.709, blends the existing
premultiplied overlay in BT.709 code values, then writes limited-range NV12.
Output header/frame metadata is BT.709, matching the converted pixels.

The transfer constants follow the [ICC sRGB registry](https://registry.color.org/rgb-registry/srgb)
and [ICC BT.709 registry](https://registry.color.org/rgb-registry/bt709).
This is an SDR conversion with reconstructed RGB clamped to [0,1], the existing
2x2 box chroma contract, and no HDR tone mapping or linear-light alpha blending.
Skia alpha is coverage and is not gamma-converted. No extra RGB image/pass is
allocated. The pre-existing BT.709 fast path retains exact transparent samples.

Transfer is selected from every actual AVFrame. The upload cannot erase it
before conversion, and a source change is not cached as the first frame's tag.
Whole-recording/danmaku export and native-Skia-only project composition accept
sRGB. A project that first blends CPU image/video layers or external libass
subtitles remains subject to the BT.709-only preflight: post-composition
conversion is insufficient for layers with different transfers. PQ/HLG/other
primaries retain their existing fallback. The render cache identity is bumped
to `vulkan-nv12-compute-v4-srgb`.

## Automated verification

- Native media tests: 147 passed, 3 GPU tests ignored in the ordinary suite.
  Loopback-network tests need host execution; their sandbox permission failures
  were rerun successfully outside the sandbox.
- Raw GPU colour oracles: 76 frames / 20,520 samples, maximum error **0 bytes**
  against independent double precision references. sRGB cases include both
  transfer knees, dark/gray ramps, coloured chroma, out-of-gamut/range samples,
  primary colours, transparent/opaque/half/mixed coverage, padded rows and
  non-workgroup-sized geometry. The old BT.709 oracle still passes unchanged.
- Eight explicit application GPU integration tests passed. The new test encodes
  tagged files, concatenates sRGB then BT.709 through MediaPlan, uses a real Skia
  PNG overlay at opacity 0 / 0.5 / 1, and exercises H.264 and HEVC hardware encode.
  Every 60-frame job reports exactly 30 sRGB conversions. Decoded NV12 samples
  agree within the two-byte encoding tolerance, and the output header is BT.709.
  Existing audio, frame order, short-tail and cancellation regressions pass.
- GLSL/SPIR-V reproducibility and `spirv-val --target-env vulkan1.2` pass.
  Native crate clippy passes. Vulkan validation still reports only the existing
  FFmpeg device-creation `VUID-VkDeviceCreateInfo-pNext-02830`; this is **not** a
  completely clean validation-layer run. No additional compute errors appeared.

## Real recording and readback audit

The local 13-minute recording is 1920x1080 / 60 fps, H.264 with AAC, limited
BT.709 matrix/primaries and sRGB transfer. Its 194 local TS segments were copied
into a temporary VOD playlist (absolute paths plus ENDLIST) and remuxed without
re-encoding. This avoids the HLS demuxer's default live-edge selection. Original
recording/cache files were not modified.

The input contains 48,460 video frames lasting 807.666667 seconds; video starts
26 ms after audio, so the container span is 807.692667 seconds. The existing
60-fps export grid covers 807.7 seconds / 48,462 frames. The comparison runner's
initial fixture duration counted only video-track duration and rejected those
two alignment frames. The validation scenario was corrected to the container
timeline; production timestamp handling was not changed.

The full recording uses the production default HEVC / speed / 10 Mbps pipeline
with synthetic 16 text + 4 PNG arrivals per second, generated by the existing
comparison fixture builder over the entire recording. These are **not the
recording's original danmaku**. Profiling and transfer auditing are enabled,
and other verification work ran concurrently, so this run is a compatibility
and load test, not a controlled speed comparison with the user's original job.

The export completed successfully with the shared GPU backend:

Detailed measurements are recorded in [`validation/macos-srgb.json`](validation/macos-srgb.json).
The ordinary and headless repository commit checks (format, clippy and tests)
also passed for implementation commit `c5c619d4`.

The audit interposes FFmpeg hardware transfers/maps. Its positive control
correctly detects 76 downloads from the two test-only GPU colour oracles
(115 uploads, zero maps). Production Skia and Metal bridge code still contains
no pixel readback / CVPixelBuffer base-address mapping. CPU NV12 uploads and
macOS GPU copies into VideoToolbox IOSurfaces remain; zero CPU readback does
not mean these transfers have been eliminated.

This pass executes macOS only. Windows uses the same shader, transfer classifier
and push constants; its plane views and Vulkan Video adapter are unchanged, but
Windows device execution has not been repeated for this change.

Unpackaged test tools select the working MoltenVK explicitly through
`BSR_VULKAN_LIBRARY`. The previously observed development-app Vulkan library
loading failure is independent of sRGB support and is not fixed by this change.
Packaged applications retain the existing bundled-runtime resolution.
